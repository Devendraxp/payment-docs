This guide walks you through everything you need to send your first payment request and interpret the response. By the end you will have created a UPI payment, confirmed its status, and inspected which gateway processed it.

<Note>
  All examples use `curl`. You can use any HTTP client — the API accepts and returns standard JSON.
</Note>

<Steps>

  <Step title="Verify the service is running">
    Before sending a payment, confirm the Payment Orchestrator and its dependencies are healthy by hitting the readiness endpoint.

    ```bash
    curl http://localhost:3000/ops/readiness
    ```

    A healthy service returns HTTP `200` with a JSON body indicating that the database and Redis connections are up:

    ```json
    {
      "status": "ok",
      "details": {
        "database": { "status": "up" },
        "redis": { "status": "up" }
      }
    }
    ```

    If any dependency reports `"status": "down"`, the service is not ready to accept payments. Check that all backing services have started before proceeding.
  </Step>

  <Step title="Create a UPI payment">
    Send a `POST /payments` request with a unique `idempotency-key` header and a JSON body describing the payment. The example below creates a ₹330.00 UPI payment on behalf of merchant `amazon`.

    ```bash
    curl -X POST http://localhost:3000/payments \
      -H "Content-Type: application/json" \
      -H "idempotency-key: pay-upi-001" \
      -d '{
        "merchantId": "amazon",
        "customerId": "cust_001",
        "amountMinor": 33000,
        "paymentMethod": "UPI",
        "instrument": { "vpa": "user@paytm", "bank": "HDFC" }
      }'
    ```

    <Note>
      `amountMinor` is expressed in the **smallest currency unit**. For INR that is paise, so `33000` equals ₹330.00. Always convert your rupee amount by multiplying by 100 before sending the request.
    </Note>

    The orchestrator scores all available gateways, routes the payment to the top-ranked healthy candidate, and returns the result synchronously:

    ```json
    {
      "paymentId": "a3f2c1d4-8b5e-4f7a-9c0e-1d2b3e4f5a6b",
      "status": "SUCCESS",
      "finalGateway": "razorpay",
      "totalAttempts": 1,
      "totalLatencyMs": 342,
      "message": "Payment completed successfully"
    }
    ```

    | Field | Description |
    |---|---|
    | `paymentId` | UUID that uniquely identifies this payment. Use it for all subsequent lookups. |
    | `status` | Final status: `SUCCESS`, `FAILED`, or `PENDING_VERIFICATION`. |
    | `finalGateway` | The gateway that ultimately processed the payment. |
    | `totalAttempts` | Total number of gateway attempts made, including retries. |
    | `totalLatencyMs` | End-to-end wall-clock time for the payment in milliseconds. |
    | `message` | Human-readable outcome description. |

    If the payment lands in `PENDING_VERIFICATION`, the gateway timed out and the outcome is being resolved asynchronously. Poll `GET /payments/{paymentId}` until the status transitions to `SUCCESS` or `FAILED`.
  </Step>

  <Step title="Retrieve the payment">
    Use the `paymentId` from the previous response to fetch the full payment record at any time.

    ```bash
    curl http://localhost:3000/payments/a3f2c1d4-8b5e-4f7a-9c0e-1d2b3e4f5a6b
    ```

    The response contains the payment details including its current status, the merchant and customer identifiers, the requested amount, and the chosen payment method.
  </Step>

  <Step title="Inspect gateway attempts">
    Retrieve the ordered list of gateway attempts to see exactly which gateways were tried, in which order, and what outcome each attempt produced.

    ```bash
    curl http://localhost:3000/payments/a3f2c1d4-8b5e-4f7a-9c0e-1d2b3e4f5a6b/attempts
    ```

    Each item in the response array includes the gateway name, attempt status, latency, and any error code returned by the gateway. When retries occur, you will see multiple attempts with earlier entries showing failure reasons and the final entry showing `SUCCESS`.
  </Step>

</Steps>

## Idempotency

Every `POST /payments` call **must** include an `idempotency-key` header. The key must be a unique string up to 128 characters that you generate on your side (a UUID or a meaningful reference such as `order-7842-payment-1` both work).

<Note>
  If you omit the `idempotency-key` header the API returns `400 Bad Request` with the message `"idempotency-key header is required"`. The request will not be processed.
</Note>

Submitting the same key with the same request body within 24 hours returns the cached response immediately — no duplicate charge is made. Submitting the same key with a **different** body returns `409 Conflict`, protecting you from accidentally reusing a key across different orders.
