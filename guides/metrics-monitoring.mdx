The metrics service (running on port `3001`) gives you a live view of how every gateway is performing. It maintains two tiers of data: **hot metrics** that reflect rolling windows of recent activity, and **historical metrics** persisted to the database for longer-term analysis. The routing engine uses hot metrics directly when scoring and ranking gateways for each payment, so the numbers you see here are the same ones driving routing decisions in real time.

## Metric Tiers

<CardGroup cols={2}>
  <Card title="Hot Metrics" icon="bolt">
    Stored in a fast in-memory store with rolling windows of 1, 5, 15, and 60 minutes. Updated after every payment attempt.
  </Card>
  <Card title="Historical Metrics" icon="database">
    Persisted for longer-term retention. Query via `GET /metrics/history/{gatewayName}` for trend analysis and longer-term reporting.
  </Card>
</CardGroup>

<Note>
  Hot metrics are **eventually consistent**. There may be a short delay between a payment attempt completing and its outcome being reflected in the rolling window. For real-time debugging, use the attempts API on the payment orchestrator (`GET /payments/{paymentId}/attempts`) to inspect the latest attempt immediately.
</Note>

## Get All Gateway Hot Metrics

Retrieve a snapshot of hot metrics for every gateway at once:

```bash
curl http://localhost:3001/metrics/gateways
```

```json
{
  "gateways": {
    "cashfree": {
      "UPI": {
        "success_rate_5m": 0.91,
        "p95_5m": 1240,
        "total_5m": 87
      },
      "CARD": {
        "success_rate_5m": 0.85,
        "p95_5m": 1850,
        "total_5m": 42
      }
    },
    "razorpay": {
      "UPI": {
        "success_rate_5m": 0.78,
        "p95_5m": 2100,
        "total_5m": 63
      }
    }
  }
}
```

## Get Metrics for a Single Gateway

Retrieve hot metrics for a specific gateway, broken down by payment method:

```bash
curl http://localhost:3001/metrics/gateways/razorpay
```

```json
{
  "gateway": "razorpay",
  "methods": {
    "UPI": {
      "success_rate_5m": 0.78,
      "p95_5m": 2100,
      "total_5m": 63
    },
    "CARD": {
      "success_rate_5m": 0.82,
      "p95_5m": 1700,
      "total_5m": 31
    }
  }
}
```

## Get Metrics for a Gateway and Method

Narrow the query to a single gateway + payment method combination:

```bash
curl http://localhost:3001/metrics/gateways/razorpay/UPI
```

```json
{
  "gateway": "razorpay",
  "method": "UPI",
  "metrics": {
    "success_rate_5m": 0.78,
    "p95_5m": 2100,
    "total_5m": 63
  }
}
```

## Understanding the Hot Metric Fields

Each response includes metrics for multiple rolling windows. The suffix on each field name indicates the window length: `_1m`, `_5m`, `_15m`, and `_60m`.

| Field pattern | Type | Description |
|---|---|---|
| `success_rate_{window}` | float (0–1) | Fraction of attempts in the window that succeeded. |
| `p95_{window}` | integer (ms) | 95th-percentile gateway response latency over the window. |
| `p50_{window}` | integer (ms) | 50th-percentile (median) gateway response latency over the window. |
| `p99_{window}` | integer (ms) | 99th-percentile gateway response latency over the window. |
| `total_{window}` | integer | Total number of attempts recorded in the window. |
| `success_{window}` | integer | Number of successful attempts in the window. |
| `fail_{window}` | integer | Number of failed attempts in the window. |
| `timeout_{window}` | integer | Number of timed-out attempts in the window. |

For example, `success_rate_5m` is the success rate over the last 5 minutes, and `p95_15m` is the p95 latency over the last 15 minutes.

## Get Historical Metrics

Query persisted historical metrics for a gateway to analyse trends over time:

```bash
curl http://localhost:3001/metrics/history/razorpay
```

Historical records include the same success rate and latency statistics as hot metrics, aggregated into time-bucketed rows.

## How Metrics Influence Routing

These hot metrics are not just for observability — they feed directly into the scoring engine that ranks gateways before every payment. The 5-minute success rate carries a **35% weight** in the overall routing score. A gateway that suddenly drops its success rate will be ranked lower within minutes, and routing will automatically shift traffic to healthier alternatives.

<Tip>
  Use the scoring debug endpoint to see exactly how current metrics are influencing gateway rankings for a specific payment context:

  ```bash
  curl "http://localhost:3000/scoring/debug?method=UPI&bank=HDFC&amountMinor=33000"
  ```

  The response shows each gateway's computed score and the individual components (including the success-rate contribution) that produced it. This is the fastest way to understand why a particular gateway is being preferred or deprioritized.
</Tip>
